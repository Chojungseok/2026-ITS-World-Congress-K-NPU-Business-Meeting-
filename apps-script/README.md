# Google Apps Script + Google Sheets 설정 안내

기존 운영용 Web App URL이 프론트엔드에 설정되어 있습니다. 이미 운영 중인 환경은 바로 아래의 갱신 절차를 따르세요. 신규 환경은 1절부터 진행합니다. **코드를 복사하는 것만으로 Google Drive나 Spreadsheet가 생성되지는 않습니다.** 최초 구축 시 운영 담당자가 Google 권한을 승인하고 setupSystem()을 실행해야 실제 DB가 만들어집니다.

## 기존 운영 환경에 이번 성능 개선 적용

이미 운영 중인 환경은 아래 순서로 이번 변경 감지 버전을 적용합니다. 기존 DB·인증정보·Web App URL을 유지합니다.

1. 현재 사용하는 **기존 Apps Script 프로젝트**를 엽니다.
2. **파일 옆 + → 스크립트**로 **Revision.gs**를 추가하고 저장소의 같은 파일 내용을 전부 복사합니다.
3. 변경된 **Code.gs, Database.gs, Setup.gs**도 각각 전체 내용으로 교체합니다. 네 파일을 함께 적용해야 합니다. 이전 성능 개선 코드도 아직 배포하지 않았다면 현재 저장소의 일곱 .gs 파일을 모두 복사하세요.
4. 기존 **SHEET_ID, TOKEN_SIGNING_SECRET, ADMIN_ID, ADMIN_PASSWORD_HASH, PROVIDER_CODE_*_HASH**, 고급 Sheets v4 서비스/매니페스트를 유지합니다.
5. **setupSystem()과 configureAuthentication()을 다시 실행하지 않습니다.** 새 속성 KNPU_REVISIONS_V1은 값이 없어도 초기 버전 0으로 읽고 첫 정상 저장 때 자동 생성됩니다. 별도 트리거나 새 시트도 필요 없습니다.
6. **배포 → 배포 관리 → 기존 웹 앱 → 수정(연필) → 버전: 새 버전 → 배포**로 갱신합니다. 코드 저장만으로는 기존 /exec에 반영되지 않습니다.
7. runtime-config.js의 기존 /exec URL을 유지한 채 변경 파일을 GitHub에 반영합니다. 새 서버는 이전 프론트엔드도 지원하므로 서버를 먼저 갱신합니다.
8. Pages 반영 후 강력 새로고침하고 [실기기 검증 절차](../docs/lightweight-change-detection.md)를 실행합니다. 이번 코드 작업에서는 실제 Google 배포나 GitHub push를 하지 않았습니다.

NPU는 5초, 관리자는 10초마다 버전만 확인합니다. 변경 없을 때 이 요청은 Google Sheets를 읽지 않습니다. ITS 신청·신청자 조회는 기존 30초 주기를 유지합니다. 실제 화면 반영시간에는 이 주기 외에 GAS/네트워크 응답시간이 더해집니다.

### 공개 설정 캐시와 수동 설정 변경

- 브라우저의 공개 config 메모리 캐시: 30초. 동시 요청은 하나의 진행 중 요청을 공유합니다.
- 서버 Script Cache의 공개 config: 30초. 신청자 개인정보/신청 목록은 이 캐시에 넣지 않습니다.
- 페이지에서 정원을 변경하면 서버 캐시를 변경 전후 무효화하고 현재 브라우저 캐시도 무효화합니다. 늦게 도착한 변경 전 응답은 새 캐시를 덮어쓰지 못합니다.
- 시트에서 **기업 설정/운영여부**를 직접 편집할 필요가 있으면 신청·승인 등의 운영을 잠시 멈춘 뒤 편집하고, Apps Script 편집기에서 **refreshPublicConfig()**를 실행하세요. 이는 공개 API가 아닌 운영자 전용 함수입니다. 자동 편집 트리거를 새로 설치하지 않습니다. 기존 브라우저까지 즉시 확인하려면 페이지를 새로고침합니다.
- 수동 변경 후 이 함수를 생략하면 NPU/관리자 revision이 바뀌지 않아 자동 갱신되지 않을 수 있습니다. 반드시 실행하거나 수동 새로고침으로 확인하세요. 공개 config를 다시 요청하는 화면에서는 서버/브라우저 캐시가 겹치면 설정 표시가 약 60초 늦을 수 있습니다. ITS에서 선택한 시간의 잔여 자리는 캐시하지 않고 약 30초마다 새로 읽습니다.
- PRIVACY_NOTICE_VERSION/PRIVACY_RETENTION_TEXT는 서버 캐시 적중 시에도 새 속성과 비교합니다. 브라우저에 이미 받은 안내는 30초 캐시 또는 페이지 새로고침 후 갱신합니다. 제출 시 서버가 안내 버전을 다시 확인합니다.
- 신청/승인/취소/정원 변경은 이 캐시를 신뢰하지 않고 잠금 안에서 실제 시트를 읽습니다. 정원 변경은 기존 NPU 화면을 사용해 검증과 처리이력을 남기세요.

## 1. 준비와 현재 구조

- 기존 화면과 해시 경로를 유지합니다. 프론트엔드는 `assets/js/api.js`만 호출합니다.
- 로컬 기본값은 mock이며 예시 데이터가 localStorage에 저장됩니다.
- GitHub Pages 등 외부 호스트에서는 GAS 모드이며 Google Sheets가 원본 데이터입니다.
- GAS URL이 없거나 서버가 실패해도 로컬 데이터로 대체하지 않습니다.
- 로컬 데모 신청은 운영 DB로 자동 복사되지 않습니다.
- 자동 이메일 발송 기능은 없습니다. 신청 완료 화면의 신청ID를 보관해야 합니다.

서버 파일 역할:

| 파일 | 역할 |
| --- | --- |
| Config.gs | 시트 열, 기본 기업·시간, 검증 함수, 공통 잠금 |
| Setup.gs | DB 자동 생성 및 기존 구조 검사 |
| Auth.gs | 운영 인증 설정, 해시 검증, HMAC 세션, 본인확인 |
| Database.gs | 요청별 batchGet snapshot, 공개 설정 캐시, 안전한 셀 쓰기, 신청·이력 일괄 저장 |
| Services.gs | 신청·취소·승인·거절·시간별 정원 규칙 |
| Code.gs | doGet/doPost와 명시적인 API 허용 목록 |
| Revision.gs | Script Properties 변경 버전, 경량 조회, 성공한 쓰기 이후 발행 |
| appsscript.json | 서울 시간대, V8, Sheets API 서비스 및 권한 |

## 2. Apps Script 프로젝트 만들기

1. DB를 관리할 Google 계정으로 [Apps Script](https://script.google.com/)에 접속합니다.
2. **새 프로젝트**를 클릭하고 이름을 `K-NPU Business Meeting Backend` 등으로 지정합니다.
3. 기본 `Code.gs` 내용을 저장소의 `apps-script/Code.gs` 전체 내용으로 바꿉니다.
4. 왼쪽 **파일 옆 + → 스크립트**로 나머지 6개 `.gs` 파일을 같은 이름으로 만듭니다. 각 파일의 내용을 그대로 복사합니다. 파일 확장자는 편집기에서 자동으로 붙을 수 있습니다.
5. 코드에 운영 승인코드, 비밀번호, Spreadsheet ID를 직접 입력하지 않습니다.

## 3. Google Sheets API 서비스 설정

신청 변경과 처리이력을 **한 번의 원자적 요청**으로 기록하기 위해 고급 Sheets API 서비스를 사용합니다.

1. 왼쪽 **프로젝트 설정(톱니바퀴)**에서 **편집기에 appsscript.json 매니페스트 파일 표시**를 켭니다.
2. 편집기로 돌아가 `appsscript.json` 내용을 이 폴더의 파일 내용으로 바꾸고 저장합니다.
3. 왼쪽 **서비스**에 `Sheets`가 표시되는지 확인합니다.
4. 표시되지 않으면 **서비스 옆 + → Google Sheets API → v4 → 식별자 Sheets → 추가**합니다.
5. 기본 Google Cloud 프로젝트에서는 서비스 추가로 관련 API가 활성화됩니다. 별도 표준 Cloud 프로젝트를 연결했다면 해당 프로젝트의 Google Cloud 콘솔에서도 Google Sheets API를 활성화해야 합니다.

[고급 서비스 공식 안내](https://developers.google.com/apps-script/guides/services/advanced), [Sheets 일괄 요청의 원자성](https://developers.google.com/workspace/sheets/api/guides/batch).

## 4. setupSystem() 실행과 권한 승인

1. 처음에는 **스크립트 속성의 SHEET_ID를 비워 둡니다.**
2. 편집기 상단 함수 목록에서 `setupSystem`을 선택하고 **실행**합니다.
3. 권한 요청이 나오면 **권한 검토 → 본인 계정 선택** 후, 이 프로젝트에 Google Sheets 접근 권한을 승인합니다.
4. 검증되지 않은 자체 개발 앱 안내가 보이면 프로젝트와 계정이 본인이 방금 만든 것이 맞는지 확인하고 Google이 제공하는 진행 절차를 따릅니다. 조직 정책으로 차단되면 Workspace 관리자에게 문의합니다.
5. 실행 로그에 `DB URL: https://docs.google.com/spreadsheets/d/...`가 표시됩니다. 링크를 엽니다.
6. **프로젝트 설정 → 스크립트 속성**에 `SHEET_ID`, `TOKEN_SIGNING_SECRET`, `PRIVACY_NOTICE_VERSION`이 생성되었는지 확인합니다.

처음 실행할 때 `K-NPU Business Meeting DB`라는 Spreadsheet를 만듭니다. 기존 `SHEET_ID`가 있으면 그것을 열어 검사하고 누락된 시트·초기 행만 보충합니다. 재실행해도 신청, 이력, 변경한 정원, 인증정보는 초기화하지 않습니다. 기존 DB에 접근할 수 없으면 중단하며 새 DB로 몰래 바꾸지 않습니다. 헤더가 다르면 기존 데이터를 덮어쓰지 않고 오류가 납니다.

서비스 설정 전에 실행하여 일부 시트까지만 만들어졌다면 서비스 설정을 완료하고 같은 `SHEET_ID`로 다시 실행하면 됩니다.

## 5. Spreadsheet는 반드시 제한됨으로 유지

생성된 Spreadsheet의 **공유 → 일반 액세스 → 제한됨(Restricted)**을 확인합니다. 필요한 ITS Korea 운영 담당자만 별도로 허용합니다.

- 링크가 있는 모든 사용자로 공개하지 않습니다.
- **웹에 게시** 기능을 사용하지 않습니다.
- NPU 기업이나 ITS 신청자에게 Spreadsheet 공유 권한을 줄 필요가 없습니다.
- Apps Script 프로젝트 편집 권한도 운영 담당자로 제한합니다. 프로젝트 편집자는 Script Properties를 볼 수 있습니다.
- 코드가 계정의 기존 공유 정책을 바꾸지는 않으므로 운영자가 이 단계를 직접 확인해야 합니다.

## 6. 새 운영 승인코드와 관리자 인증정보

**프로젝트 설정 → 스크립트 속성 → 스크립트 속성 추가**에서 다음 값을 입력합니다. 비밀번호를 GitHub, HTML, JavaScript, 채팅에 붙여 넣지 않습니다.

| 속성 이름 | 입력할 값 |
| --- | --- |
| PROVIDER_CODE_DEEPX | 딥엑스에 전달할 새로운 승인코드 |
| PROVIDER_CODE_MOBILINT | 모빌린트에 전달할 새로운 승인코드 |
| PROVIDER_CODE_FURIOSA | 퓨리오사에 전달할 새로운 승인코드 |
| PROVIDER_CODE_REBELLIONS | 리벨리온에 전달할 새로운 승인코드 |
| ADMIN_ID | 새로운 운영 관리자 ID, 최대 64자 권장 |
| ADMIN_PASSWORD | 새로운 운영 관리자 비밀번호 |

비밀번호 관리 도구 등으로 기업마다 서로 다른 무작위 코드를 만드세요. 코드/비밀번호는 **12~128자**이며 공개된 로컬 데모 값은 서버가 거부합니다. 관리자 ID도 로컬 데모 ID와 다르게 설정합니다.

입력 후 함수 목록에서 **`configureAuthentication`을 선택하고 실행**합니다.

- 서버 비밀키로 인증정보를 HMAC 해시화하여 `PROVIDER_CODE_*_HASH`, `ADMIN_PASSWORD_HASH` 속성으로 저장합니다.
- 입력한 평문 승인코드/비밀번호 속성은 삭제합니다. 이는 정상 동작입니다.
- `ADMIN_ID`는 Script Properties에 유지됩니다.
- 코드가 승인코드/비밀번호를 실행 로그에 출력하지 않습니다. 운영자가 원본 코드를 안전하게 보관하여 각 담당자에게 전달해야 합니다.
- 성공하면 기존 세션을 모두 폐기합니다.
- 일부 코드 교체 시 해당 평문 속성만 다시 추가한 뒤 이 함수를 실행합니다. 다른 기존 해시는 보존합니다.
- `TOKEN_SIGNING_SECRET`은 setupSystem이 자동 생성합니다. 프론트엔드로 복사하지 마세요. 이를 직접 바꾸면 기존 토큰과 인증 해시가 무효화되므로 모든 실제 인증정보를 다시 입력하고 configureAuthentication을 실행해야 합니다.

로그인 실패는 계정별 15분 구간에서 10회까지 허용합니다. 이후 15분 구간 만료까지 인증이 제한됩니다. 기존 정상 로그인 세션은 이 실패 횟수와 별개입니다.

## 7. 개인정보 안내 설정

Script Properties에서 다음을 관리합니다.

| 속성 | 의미 |
| --- | --- |
| PRIVACY_NOTICE_VERSION | 초기값 knpu-2026-v1. 동의문이나 보유기간이 바뀌면 새 버전으로 변경 |
| PRIVACY_RETENTION_TEXT | **ITS Korea가 확정한 보유·이용 기간 문구** |

보유기간은 임의로 정하지 않았습니다. 값이 없으면 화면에 **운영기관 확인 후 안내 예정**이 표시됩니다. **실제 개인정보 접수 전에 운영기관이 보유기간과 최종 동의문을 확정하고 이 설정을 입력해야 합니다.** 이 코드는 법적 보유기간이나 제3자 제공 여부를 추정하지 않습니다. 동의문 변경 시 버전을 올리고 이전 안내문 원문은 운영기관이 별도로 보관하세요.

공개 getConfig는 버전과 안내 문구만 전달합니다. 신청에는 동의 여부, 서버 동의시각, 해당 버전이 기록됩니다. 오래된 버전으로 제출하면 다시 안내문을 확인하도록 거부합니다.

- 상담신청: 신청ID / 신청일시 / ITS기업명 / 담당자명 / 연락처 / 이메일 / NPU기업ID / NPU기업명 / 상담시간 / 참석인원 / 상담내용 / 상태 / 개인정보동의 / 개인정보동의시각 / 개인정보안내문버전 / 최종수정일시
- 시간대별정원: NPU기업ID / NPU기업명 / 상담시간 / 최대상담건수 / 운영여부 / 최종수정일시 / 최종수정자
- 처리이력: 이벤트ID / 처리시각 / 처리유형 / 처리자역할 / 처리자 / 신청ID / ITS기업명 / NPU기업ID / 상담시간 / 변경전상태 / 변경후상태 / 변경전정원 / 변경후정원
- NPU설정: NPU기업ID / NPU기업명 / 영문명 / 활성여부

기본 NPU: `deepx` 딥엑스 5 / `mobilint` 모빌린트 2 / `furiosa` 퓨리오사 1 / `rebellions` 리벨리온 2.

각 기업에 `16:50 – 17:00`, `17:00 – 17:10`, `17:10 – 17:20`, `17:20 – 17:30` 네 행을 생성하므로 초기 정원 설정은 총 16행입니다. 운영여부는 TRUE로 생성됩니다. NPU 설정의 활성여부가 FALSE인 기업은 새 신청/로그인을 받지 않으며 기존 이력은 관리자에게 남습니다.

서버 시각은 ISO UTC 문자열로 저장하고 화면에서는 한국 시간으로 표시합니다. 시트의 문자열 시각 끝에 Z가 붙어 있어도 오류가 아닙니다. Spreadsheet 시간대 자체도 Asia/Seoul입니다.

정원 변경은 NPU 페이지의 시간별 변경 기능을 사용하세요. 직접 시트에서 신청 상태나 정원을 수정하면 서버 잠금/검증/감사 기록을 우회합니다. 운영 중에는 직접 수정하지 않습니다. 승인대기는 정원을 차지하지 않고 매칭확정만 집계합니다. 참석인원과 상담 건수는 별개입니다.

## 9. Web App 배포

1. Apps Script 우측 상단 **배포 → 새 배포**를 누릅니다.
2. 유형 선택(톱니바퀴)에서 **웹 앱**을 고릅니다.
3. 설명에는 운영 버전 등을 입력합니다.
4. **다음 사용자로 실행(Execute as): 나(Me, DB를 소유한 계정)**로 설정합니다.
5. **액세스 권한이 있는 사용자(Who has access): 모든 사용자(Anyone)**로 설정합니다. 신청자는 Google 로그인이 없어야 하므로 Google 계정 사용자만 허용하는 설정과 구별하세요.
6. **배포**를 누르고 필요한 권한을 승인합니다.
7. **웹 앱 URL** 중 `https://script.google.com/macros/s/.../exec` 주소를 복사합니다. 배포 ID 단독 값이나 개발용 `/dev` 주소를 사용하지 않습니다.

외부 웹 앱 호출 허용과 Spreadsheet 공개는 다릅니다. 엔드포인트는 공개되지만 신청 목록/개인정보 API는 자체 인증을 요구하고 Sheet는 제한됨으로 유지합니다. Workspace 정책상 익명 웹 앱 배포가 불가능하면 조직 관리자 확인이 필요합니다. 이 경우 무인증 접근이 가능한 것처럼 성공 처리하지 않습니다.

[웹 앱 공식 배포 안내](https://developers.google.com/apps-script/guides/web).

코드 수정 후에는 **배포 → 배포 관리 → 기존 배포 수정(연필) → 버전: 새 버전 → 배포**를 해야 /exec에 반영됩니다. 기존 배포를 갱신하면 URL을 유지할 수 있습니다. 인증정보·보유기간 등 Script Properties의 변경은 코드 배포와 별개입니다.

## 10. 프론트엔드 URL 연결과 로컬 확인

`assets/js/runtime-config.js` 한 곳의 `gasUrl`에 복사한 /exec 주소를 입력합니다.

```js
export const RUNTIME_CONFIG = Object.freeze({
  backend: 'auto',
  gasUrl: 'https://script.google.com/macros/s/여기에_배포_ID/exec',
  refreshIntervalMs: 30000,
  revisionPolling: Object.freeze({ providerMs: 5000, adminMs: 10000, retryMs: 30000 })
});
```

위 코드는 위치 설명용입니다. 파일 아래의 resolveBackend 함수는 지우지 마세요. URL에는 토큰, 비밀번호 또는 추가 쿼리를 넣지 않습니다.

- `auto`: localhost/127.0.0.1은 mock, GitHub Pages 등 외부 호스트는 GAS.
- 로컬에서 **실제 DB 연결**을 먼저 확인하려면 잠시 `backend: 'gas'`로 바꾸고 `npm start` 후 열어보세요.
- 로컬 mock으로 돌아가려면 `auto`로 복원합니다.
- 공개 사이트에서 명시적인 mock 모드를 사용하려 하면 오류로 차단합니다.
- 주소가 비어 있거나 잘못되면 운영 설정 안내가 표시되고 개인정보를 localStorage에 저장하지 않습니다.

설정 직후 새로고침합니다. 기존 브라우저의 데모 신청은 서버 DB와 무관하며 자동 업로드되지 않습니다.

## 11. GitHub Pages에 연결

Google 설정과 로컬 GAS 모드 테스트를 먼저 완료합니다. 실제 운영 비밀번호를 저장소에 넣지 않은 것을 확인한 뒤 변경한 코드와 공개 gasUrl을 GitHub에 커밋/푸시합니다.

저장소: [Chojungseok/2026-ITS-World-Congress-K-NPU-Business-Meeting-](https://github.com/Chojungseok/2026-ITS-World-Congress-K-NPU-Business-Meeting-)

1. 저장소의 **Settings → Pages**에 들어갑니다.
2. Build and deployment의 Source를 **Deploy from a branch**로 지정합니다.
3. Branch는 **main**, 폴더는 **/(root)**로 설정하고 저장합니다.
4. 배포가 끝나면 Pages 설정에서 표시하는 **Visit site** 주소를 사용합니다.
5. 사이트에서 강력 새로고침 후 운영 문구와 실제 DB 동작을 확인합니다.

별도 빌드는 없습니다. 상대 경로와 해시 라우팅, 루트의 .nojekyll을 그대로 유지합니다. 기존 Pages가 이미 켜져 있다면 main에 푸시하면 자동 배포될 수 있으므로 **gasUrl을 채우기 전의 운영 전환 코드를 먼저 푸시하지 않는 편이 좋습니다.** 이 작업에서는 Pages 설정이나 Google 리소스를 변경하지 않았습니다.

## 12. 모바일 → PC 테스트 순서

처음에는 실제 개인정보 대신 예시 정보로 테스트하세요. 모바일과 PC가 **동일한 Pages URL과 같은 GAS 배포 URL**을 사용하는 것이 중요합니다.

1. 모바일에서 상담 신청: 예시 기업/이메일을 입력하고 동의 후 제출합니다. 신청ID를 복사합니다.
2. Spreadsheet의 상담신청 시트에 동일한 ID의 승인대기 행과 처리이력의 신청 행이 생겼는지 확인합니다.
3. PC에서 같은 사이트 하단 관리자 로그인 → 새 운영 ID/비밀번호로 로그인합니다. 모바일에서 신청한 기업과 ID가 보여야 합니다.
4. 다른 브라우저에서 해당 NPU로 로그인합니다. 해당 기업 신청만 표시되어야 합니다.
5. NPU에서 승인 → 모바일 신청 현황 확인에서 **ID + 이메일**로 조회합니다. 매칭확정이어야 합니다.
6. NPU에서 특정 시간 정원을 변경합니다. 이미 열려 있는 ITS 신청 화면에서 약 30초 주기로 반영되는지 확인합니다. 다른 시간은 유지되어야 합니다.
7. 확정 신청을 ID + 이메일로 취소합니다. 잔여 자리가 1 증가하고 관리자 로그에 취소가 표시되어야 합니다.
8. 신청ID만 전송하거나 틀린 이메일을 넣어 조회/취소할 수 없는지 확인합니다.
9. 관리자 로그아웃 후 전체 목록 접근이 차단되는지, NPU 토큰으로 관리자 API/다른 기업 신청 변경이 차단되는지 확인합니다.
10. 정원 1인 시간에 대기 신청 두 건을 만든 뒤 두 NPU 브라우저에서 동시에 승인합니다. 한 건만 확정되어야 합니다. 정원 축소와 승인, 승인과 취소도 동시에 확인합니다.
11. 관리자 표의 잔여 건수를 눌러 목록→신청 상세→목록 돌아가기와 로그 복합 필터를 확인합니다.
12. 페이지를 새로고침하면 NPU/관리자는 sessionStorage의 유효한 토큰으로 복원됩니다. 30분 후에는 다시 로그인해야 합니다. 신청자 개인정보는 브라우저 영구 저장소에 저장하지 않습니다.

자동 갱신은 화면이 보이는 동안만 실행됩니다. NPU 정원 초안과 관리자 필터는 그대로 두고 목록/통계를 갱신합니다. 열린 읽기 전용 상세 팝업도 최신 상태로 바꾸며, 팝업에 직접 편집 가능한 입력값이 있으면 그 내용은 덮어쓰지 않습니다. 신청자 lookup의 입력/확인 팝업과 실제 변경 처리 중에는 갱신을 미룹니다. 숨긴 탭으로 돌아오면 즉시 버전을 확인합니다. 새로고침 버튼/화면 재진입으로도 최신값을 읽을 수 있습니다. 서버는 제출/승인 순간 정원을 다시 검증하므로 화면이 잠깐 오래된 값이어도 초과 승인되지 않습니다.

## 13. 통신·보안·오류 처리

- 공개 GET: getConfig, getAvailability, getAvailabilityRevision. 개인정보/신청ID/토큰을 GET 쿼리로 보내지 않습니다.
- 나머지는 `POST` + `Content-Type: text/plain;charset=utf-8` JSON 본문입니다.
- 쿠키/Authorization 헤더를 보내지 않아 불필요한 preflight를 피합니다. 토큰은 POST 본문에만 둡니다.
- ContentService 응답의 Google 리다이렉트를 follow하고 JSON 결과를 읽습니다. `no-cors`나 JSONP를 사용하지 않습니다.
- 응답: `{ok:true,data:...}` 또는 `{ok:false,error:{code,message}}`.
- 45초 응답 제한. 연결 실패 시 성공으로 처리하지 않으며 쓰기를 자동 재시도하지 않습니다. 응답이 끊겨도 서버 반영은 끝났을 수 있으므로 먼저 조회/관리자 화면에서 결과를 확인합니다.
- 잘못된 이메일과 없는 ID는 같은 오류입니다. ID는 UUID이며 조회 시도 제한도 있습니다. 이메일 소유권 OTP까지 구현한 것은 아닙니다.
- NPU/관리자 토큰은 HMAC-SHA256 서명, role/providerId/expiresAt/jti와 서버 활성 세션 확인을 거칩니다. 로그아웃한 토큰은 서버에서 폐기됩니다. 클라이언트가 보낸 providerId로 권한을 결정하지 않습니다.
- 브라우저에는 토큰만 sessionStorage에 저장합니다. 실제 승인코드/비밀번호/Google 인증정보/서명 비밀키는 프론트엔드로 배포하지 않습니다.
- 조회용 전체 목록은 관리자 또는 해당 NPU 인증 후에만 전달합니다.
- 신청·승인·거절·취소·정원 변경, 인증/로그아웃/본인확인은 공통 ScriptLock을 유지합니다. 공개 조회와 기업/관리자 단일 목록의 불필요한 잠금은 제거했습니다. 관리자 overview는 일관된 네 시트 snapshot을 읽는 구간만 잠급니다. 신청 변경 + 처리이력은 Sheets batchUpdate 한 번에 저장합니다. 사용자 입력은 stringValue로 기록하므로 수식으로 실행되지 않습니다.
- 서버 내부 예외/stack trace/원시 요청을 클라이언트나 사용자 코드의 로그에 남기지 않습니다. 성공적인 setup의 DB URL 로그만 운영자에게 출력합니다.
- Apps Script/Sheets의 사용량 제한과 조직 접근 정책은 별도로 적용됩니다. 익명 공개 접수에 CAPTCHA는 포함하지 않았습니다. 로그인 제한은 계정별이며 조회 제한은 Apps Script CacheService를 사용하는 보조 제한입니다. 대규모 행사·악성 트래픽 방어를 위한 운영 부하 검증은 별도입니다.

[ContentService 리다이렉트 공식 설명](https://developers.google.com/apps-script/guides/content).

## 14. 오류 해결과 남은 점검

| 증상 | 확인할 내용 |
| --- | --- |
| 운영 서버 URL 설정 안내 | runtime-config.js의 gasUrl에 정확한 /exec 주소 입력 |
| Sheets is not defined / setup 실패 | 고급 Sheets API 서비스, 매니페스트, Google 권한 승인 |
| JSON 대신 로그인 HTML / CORS 오류 | 웹 앱 Execute as Me, Anyone 권한, /exec, 조직 정책. 최신 배포와 실제 Pages origin에서 재시험 |
| SETUP_REQUIRED | SHEET_ID, 접근 권한, 4개 시트 헤더 순서 확인 후 setupSystem 재실행 |
| INVALID_CREDENTIALS | 로컬 데모 코드가 아닌 새 운영 코드, configureAuthentication 실행 여부 |
| UNAUTHORIZED | 30분 만료, 로그아웃, 인증정보 교체에 의한 세션 해제. 재로그인 |
| CAPACITY_FULL | 실제 확정 건수/정원/운영여부를 새로고침 |
| NOTICE_CHANGED | 페이지 새로고침 후 바뀐 개인정보 안내와 동의 재확인 |
| NETWORK_ERROR | 자동 재제출하지 말고 기존 처리 결과부터 확인 |
| REVISION_PENDING이 계속 발생 | 저장과 버전 발행 사이 동기화 미완료. 앱은 30초 이상 지속 시 제한된 전체 조회로 보완합니다. 실제 신청/이력 결과를 확인하고 편집기에서 refreshPublicConfig()를 실행하면 모든 버전을 다시 발행합니다. setup/auth 재설정은 하지 않습니다. |
| RATE_LIMITED | 제한 구간이 지난 뒤 인증정보 확인 후 재시도 |

**신규 구축 시 확인:** Google 권한 승인 및 DB 생성, 제한됨 공유, 운영 코드 발급, 보유기간 확정, 백업·접근권한·행사 종료 후 처리 방침.

**이번 버전 갱신 후 확인:** 동일한 /exec의 새 버전 배포, Pages 반영, 실제 origin의 GET/POST/리다이렉트/JSON/CORS, 두 기기의 공유와 마지막 자리 동시 승인, 호출 수와 응답 속도. 공개 설정 캐시가 있어도 실제 정원 검증은 최신 DB를 사용하는지 위 흐름으로 확인합니다.

로컬 검증: Node 테스트 65개, 기존 모바일/PC 회귀·성능 검사와 신규 변경 감지 브라우저 검사 통과. [변경 감지 결과와 재현 방법](../docs/lightweight-change-detection.md)을 참고하세요.

로컬 자동 테스트는 실제 .gs 파일을 Google 서비스 모형에서 실행합니다. 실제 Google 서비스의 CORS, 권한, 할당량, 네트워크 경합을 검증한 결과가 아닙니다. 서버/URL 설정 후 이 문서의 실기기 테스트를 반드시 진행하세요.
